# Автоматизатор PomidorQA — пошаговый workflow

Ты пишешь Playwright-тесты для репо PomidorQA. Твой результат неотличим от эталонных тестов репо и зелёный локально. Каждый шаг ниже обязателен.

## Шаг 0. Контекст проекта (всегда первым)
1. Прочитай `codex.md` в корне репо — карта репозитория, конвенции, команды, ESLint-правила. Дальше действуй строго по нему.
2. Прочитай `README.md`, если задача непонятна без контекста курса.

## Шаг 1. Найти образец («по образу и подобию»)
1. Glob по `tests/e2e/*.spec.ts`, выбери 1–2 ближайших по смыслу спека (по страницам/фичам из задачи).
2. Прочитай их и их page objects (`tests/pages/`).
3. Сформируй в голове план теста в терминах существующих паттернов: `describe` → `beforeEach` (`registerViaApi`) → `afterEach` (`deleteAccountViaApi`) → русские `test.step`.

## Шаг 2. Собрать локаторы через Playwright MCP
Не выдумывай локаторы по памяти — сними их с живого стенда:
1. `browser_navigate` на страницу: `https://aiqa.su` + путь из `ROUTES` (`tests/helpers/user.ts`). Если нужен залогиненный вид — зарегистрируй/залогинь юзера через UI в браузере MCP.
2. `browser_snapshot` → выпиши роли, имена, подписи и `data-testid` нужных элементов.
3. Составь семантические локаторы (`getByRole` / `getByLabel` / `getByText` / `getByTestId`). Если элемент без семантики — это кандидат на `data-testid`: зафиксируй и упомяни в отчёте, не молча обходи CSS-селектором.
4. Проверь каждый новый локатор действием через MCP (`browser_click`, `browser_type`) и только потом неси в код.

Шпаргалка: `references/locator-cheatsheet.md`.

## Шаг 3. Написать код
1. Если локатор новый — добавь его в **page object** (`tests/pages/<страница>.ts`) по стилю существующего класса: `readonly`-поля, сборка в конструкторе, методы-действия.
2. Общие шаги (логин, данные) — в `tests/helpers/user.ts`, не копипастой.
3. Напиши spec в `tests/e2e/<тема>.spec.ts` по образцу из шага 1:
   - русское название теста, русские `test.step`,
   - `makeUser(role)` / `makeUnique()`, без хардкодов,
   - ожидания только auto-waiting (`expect(locator)...`, `toPass`, `expect.poll`).
4. Импорты относительные (`'../helpers/user'`, `'../pages/<page>'`).

## Шаг 4. Линтер
```bash
npx eslint <изменённые файлы> --fix
```
Оставшиеся ошибки чини руками. Запрещено гасить правилами-исключениями (`eslint-disable`) — правила в `eslint.config.mjs` уровня error не отключаются. Линтер зелёный → шаг 5.

## Шаг 5. Прогон и цикл фиксов
```bash
npx playwright test <твой spec-файл>
```
Упал:
1. Читай текст ошибки; для e2e — trace и артефакты в `test-results/<тест>/` (`trace.playwright.zip` → `npx playwright show-trace` недоступен агенту — читай `error-context.md`/скриншоты из артефактов, либо перезапусти с `--trace on` и смотри `browser_snapshot` через MCP на проблемном шаге).
2. Определи причину: неверный локатор → пересними через MCP (шаг 2); гонка/тайминг → auto-waiting вместо пауз; данные → `makeUnique`.
3. Почини и перезапусти.

Повторяй до зелёного, **максимум 5 итераций**. Не зеленеет — остановись и отчётливо сообщи: что пробовал, гипотезы, что нужно человеку.

## Шаг 6. Регресс
Локально зелёный → прогони смежные спеки (те же page objects) или весь `npm run test:e2e`, чтобы убедиться, что ничего не сломано.

## Шаг 7. Отчёт
Обязательно укажи:
- какие файлы созданы/изменены и зачем;
- какие локаторы собраны через MCP и с каких страниц;
- команды линта и прогона + их результат (цитируй итог: «X passed»);
- что осталось за пределами задачи (баги сайта, отсутствие семантики, необходимость testid).
