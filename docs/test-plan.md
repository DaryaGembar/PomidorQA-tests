# Test Plan — PomidorQA

Документ описывает, **что** тестируется, **как**, **когда** считается готовым и **где** живут артефакты.
Трассировка до конкретных требований и тестов — в [coverage-matrix.md](./coverage-matrix.md).

**Стенд:** `https://aiqa.su/pomidorqa` (production-like, стабильный).
**Срез:** ветка `main`, обновляется при изменении требований.

---

## 1. Цель

Подтвердить, что продукт PomidorQA соответствует требованиям MVP
и безопасен для использования реальными пользователями:
бронирование, отмена, каталог, профиль работают предсказуемо,
включая граничные случаи и конкурентные сценарии.

## 2. Scope

### В scope
- Регистрация / вход / сессия (раздел 4 требований)
- Профиль: поля, навыки обоих типов, часовой пояс (раздел 5, 6)
- Слоты доступности (раздел 7)
- Каталог участников и страница участника (раздел 8, 9)
- Бронирование звонка и отмена (раздел 10, 11)
- Список «Мои встречи» (раздел 12)

### Out of scope
- Код продукта — закрыт, тестируется только через UI и наблюдаемые контракты
- Мобильные нативные клиенты (только адаптивная вёрстка в браузере)
- Нагрузочное тестирование — вне MVP
- Тестирование безопасности (XSS/CSRF) — вне MVP

## 3. Стратегия

Тестирование идёт **по тестовой пирамиде** — снизу дешевле, сверху ценнее как сценарий.

| Уровень | Что покрывает | Файл / расположение | Назначение |
| --- | --- | --- | --- |
| **Unit** | Чистые функции: пересечение слотов, форматирование времени, валидация пароля | `src/pyramid/`, `tests/unit/` | Быстрые проверки контрактов, граничные случаи «впритык» |
| **API** | Бизнес-правила бронирования: успех, свои/чужие слоты, гонка | `src/pyramid/mock-booking-api.ts`, `tests/api/` | Детерминированная проверка серверных правил через HTTP к моку |
| **E2E** | Сквозные пользовательские сценарии в реальном Chromium | `tests/e2e/` | Доказательство, что продукт в целом работает так, как увидит пользователь |

**Мануальное тестирование** — для исследования новых сценариев, баг-репортов по визуальным/UX-проблемам
и для проверок, которые в автотесты невыгодно.

## 4. Entry / Exit criteria

### Entry (когда начинаем прогон)
- Стенд доступен, проходит smoke-проверку загрузки главной страницы
- Тестовые эндпоинты для регистрации/удаления отвечают
- В CI зелёный lint и unit

### Exit (когда считаем прогон успешным)
- Все `automated` и `partial` тесты зелёные
- Известные дефекты (KD-1) подтверждены в актуальной версии продукта или помечены `test.fail()`
- Allure-отчёт сгенерирован, приложен к прогону
- Ни одного `not covered` требования не появилось без пересмотра матрицы

### Приостановка прогона
- Стенд вернул 5xx на smoke — прогон не имеет смысла, чиним стенд
- Боевой релиз продукта сломал сценарии, которые раньше были стабильны — эскалация

## 5. Окружение

| Слой | Конфигурация |
| --- | --- |
| **Браузер E2E** | Chromium (Playwright bundled), single project |
| **API** | Локальный мок-сервер `src/pyramid/mock-booking-api.ts`, поднимается на фикстуре |
| **Unit** | Node.js, без сети и браузера |
| **Параллелизм** | E2E — 2 воркера в CI, локально — по умолчанию Playwright |
| **Учётные данные** | Генерируются на каждый прогон (`makeUnique`, `makeUser`), каскадная уборка в `finally` |

Переопределение стенда:
```bash
POMIDORQA_BASE_URL=http://localhost:3000 npx playwright test --project=e2e
```

## 6. Тестовые данные

- **Уникальность** — каждый прогон получает свежих пользователей и навыки, чтобы не конкурировать
  на общем стенде с другими CI-прогонами и локальными запусками.
- **Регистрация** — через тестовые API-эндпоинты, не через UI (быстрее и стабильнее).
- **Уборка** — `deleteAccountViaApi` в `afterEach`/`finally`, каскад: навыки → слоты → брони.
- **Чужие данные** — не читаем, не модифицируем; любые ассерты только на созданных нами сущностях.

## 7. Риски

| Риск | Вероятность | Импакт | Митигация |
| --- | --- | --- | --- |
| Стенд недоступен | Средняя | Прогон блокируется | Smoke перед прогоном; `test.fixme` с привязкой к тикету |
| Продукт обновился и сломал UI | Средняя | Падение e2e | Сначала CI как canary, потом расширяем зону |
| Гонка за слот — flaky на нагрузке | Низкая | Ложный 409 | Тест гонки на API-моке детерминирован; на UI — `test.slow()` и явные ожидания |
| Гидрация React — клики до загрузки | Средняя | Тихий no-op | Решено: ретраи клика до ответа сервера в page objects; см. BR-001 |

## 8. Артефакты

| Артефакт | Где | Как используется |
| --- | --- | --- |
| **Allure-отчёт** | [GitHub Pages](https://daryagembar.github.io/PomidorQA-tests/) — тренды, шаги, вложения | Ревью прогона, история |
| **Playwright HTML** | `playwright-report-*` в артефактах CI run | Детальный разбор падений |
| **Trace / скриншоты** | `test-results/`, в архиве CI run | Расследование инцидентов |
| **JUnit** | Комментарий в PR | Сводка по `e2e` без открытия отчёта |
| **Telegram-уведомления** | Канал `@DaryaGembar_bot` | Быстрый сигнал о статусе, длительностях, артефактах падений |
| **AI-reviewer** | Комментарий в PR после зелёного CI | Двухпроходная проверка против [TEST-CODEX](./TEST-CODEX.md) и [REVIEW](./REVIEW.md) |
| **Bug Reports** | [docs/bug-reports/](./bug-reports/) | Формализация дефектов продукта и инфраструктуры |

## 9. Роли

| Роль | Ответственность |
| --- | --- |
| **AQA** (Гембар Дарья) | Дизайн тестов, поддержка пирамиды, ревью CI|
| **Product owner** | Источник и приоритизация требований, эскалация продуктовых решений |
| **AI-reviewer** | Дополнительная проверка PR по `TEST-CODEX` + `REVIEW` чеклисту |

## 10. Расписание

- **Каждый push в `main`** — полный прогон: lint → unit → api → e2e → allure → notify
- **Каждый PR** — тот же пайплайн + AI-reviewer
- **Ad-hoc** — ручной прогон уровня при инциденте на стенде
