# Test Cases — PomidorQA

Примеры тест-кейсов в стандартном формате. Каждый кейс привязан к требованию и к автоматизированному
покрытию (если есть). Используются как основа для ручных чек-листов, регресса и ревью.

**Где живут автотесты:** [coverage-matrix.md](./coverage-matrix.md) — там же статусы `automated` /
`partial` / `manual` для каждого требования.

**Статусы ниже:**
- `Automated` — закрыт автотестом, ручной прогон не обязателен
- `Manual only` — намеренно ручной (не наблюдаемо через интерфейсы или разово)
- `Exploratory` — формат чартера, без жёстких шагов

## TC-001 — Главная страница доступна без авторизации (Smoke)

| Поле | Значение |
| --- | --- |
| **Priority** | High |
| **Type** | Smoke |
| **Требование** | Раздел 3 (R3.1, R3.2) |
| **Автоматизация** | Частично: `e2e/guest-access` |
| **Preconditions** | Чистый контекст браузера, без cookies, без авторизации |
| **Steps** | 1. Открыть `https://aiqa.su/pomidorqa` |
|  | 2. Дождаться полной загрузки DOM |
|  | 3. Проверить наличие шапки, каталога, футера |
| **Expected** | Страница отображается без ошибок в консоли; ссылки в каталоге кликабельны; CTA «Зарегистрироваться» виден |
| **Pass criteria** | Нет 4xx/5xx; в Network нет failed запросов; |

## TC-002 — Регистрация с уже занятым email в разном написании (Negative)

| Поле | Значение |
| --- | --- |
| **Priority** | High |
| **Type** | Negative |
| **Требование** | R4.4 |
| **Автоматизация** | Частично: только полное совпадение email в `e2e/register-form` |
| **Preconditions** | Зарегистрирован пользователь `darya@example.com` |
| **Steps** | 1. Открыть форму регистрации |
|  | 2. Попытка 1: `Darya@Example.com` (разный регистр) |
|  | 3. Попытка 2: ` darya@example.com ` (пробелы по краям) |
|  | 4. Попытка 3: `darya+alt@example.com` (sub-addressing, если поддерживается) |
| **Expected** | 2 и 3 — отказ с тем же сообщением, что и в R4.4 (не раскрывать, что email уже существует, если политика скрытия работает единообразно). 4 — поведение по решению продукта |
| **Pass criteria** | Не создан второй аккаунт; сообщение не уточняет «уже существует», если такое поведение заявлено |

## TC-003 — Время слотов в разных часовых поясах (Functional)

| Поле | Значение |
| --- | --- |
| **Priority** | High |
| **Type** | Functional / Boundary |
| **Требование** | R5.3, R5.5 |
| **Автоматизация** | `partial`: `e2e/profile-flow` — список из 10 поясов; `unit/slots` — `formatSlotTime` |
| **Preconditions** | Авторизованный хост с одним слотом, например, на 12:00 UTC |
| **Steps** | 1. Открыть профиль хоста, переключить часовой пояс на `Europe/Moscow` (UTC+3) |
|  | 2. Открыть публичную страницу участника как гость |
|  | 3. Зафиксировать время слота на карточке |
|  | 4. Вернуться в профиль, переключить на `Asia/Kamchatka` (UTC+12) |
|  | 5. Обновить публичную страницу участника |
|  | 6. Зафиксировать время |
| **Expected** | Время слота в каждом поясе = `UTC+offset` от исходного времени, без регрессии в UTC или пояс хоста |
| **Pass criteria** | Сдвиг = разница поясов (для MSK и KAMT — +9 часов). Формат HH:mm, без AM/PM |

## TC-004 — Профиль с большим объёмом «О себе» (Negative / Visual)

| Поле | Значение |
| --- | --- |
| **Priority** | Medium |
| **Type** | Negative / Visual |
| **Требование** | R5.4 |
| **Автоматизация** | Manual only |
| **Preconditions** | Авторизованный пользователь |
| **Steps** | 1. Открыть редактирование профиля |
|  | 2. Ввести в «О себе» строку длиной 2000 символов |
|  | 3. Ввести строку с HTML/JS: `<img src=x onerror=alert(1)>` |
|  | 4. Ввести строку с переводами строк, эмодзи, RTL-текстом |
|  | 5. Сохранить, перезагрузить страницу |
| **Expected** | Текст не обрезан посередине слова; HTML не интерпретируется (видна разметка, нет alert); переводы строк сохраняются; эмодзи и RTL отображаются без «кракозябр» |
| **Notes** | Если есть серверный лимит — проверить его; задокументировать. Это кейс и на безопасность (XSS), и на UX (обрезка/перенос) |

## TC-005 — Бронирование слота ровно за 2 часа до начала (Boundary)

| Поле | Значение |
| --- | --- |
| **Priority** | High |
| **Type** | Boundary |
| **Требование** | R10.2, R11.2 |
| **Автоматизация** | Manual only (флаки вокруг часовой границы) |
| **Preconditions** | Хост с тремя слотами: T+1ч, T+2ч, T+2ч01м |
| **Steps** | 1. Гость бронирует T+1ч — должен быть доступен |
|  | 2. Гость бронирует T+2ч — поведение зависит от того, как округляется граница «2 часа» |
|  | 3. Гость бронирует T+2ч01м — должен быть доступен |
| **Expected** | T+2ч — поведение по решению продукта (≤, <, ровно 2:00). Зафиксировать фактическое правило |
| **Notes** | Если правило «строго < 2ч», слот T+2ч отменяем, остальные доступны. Если «≤ 2ч», наоборот |

## TC-006 — Каталог не показывает участника без будущих слотов (Edge case)

| Поле | Значение |
| --- | --- |
| **Priority** | High |
| **Type** | Functional / Edge |
| **Требование** | R8.1 |
| **Автоматизация** | `e2e/catalog-search` |
| **Preconditions** | Участник A: 1 слот в прошлом. Участник B: 1 слот в будущем |
| **Steps** | 1. Гость открывает каталог |
|  | 2. Ищет по навыку участника A |
|  | 3. Ищет по навыку участника B |
| **Expected** | A — нет в выдаче. B — есть. После добавления B нового слота в прошлое — тоже исчезает |
| **Pass criteria** | Каталог всегда показывает только тех, у кого есть `free` слот в будущем |
