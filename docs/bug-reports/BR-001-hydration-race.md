# BR-001 — Кнопка кликабельна до завершения гидрации React (тихий no-op)

| Поле | Значение |
| --- | --- |
| **Severity** | S2 — критично |
| **Priority** | P1 |
| **Type** | Functional / UX |
| **Status** | Fixed (митигация в тестах; ожидает продуктовой починки) |
| **Component** | Любые action-кнопки после перезагрузки страницы (например, «Забронировать», «Сохранить», «Добавить слот») |
| **Reported by** | AQA, ~21.09.2026 (найдено по трейсу падения e2e) |
| **Environment** | `https://aiqa.su/pomidorqa`, Chromium (Playwright) |
| **Related requirement** | Косвенно R10.* (бронирование), R7.* (слоты) — любые действия с persisted state |

### Summary
После перезагрузки страницы кнопки действий (например, «Забронировать») визуально активны
и реагируют на клик, но обработчик ещё не подключён — клик уходит в пустоту, запрос не отправляется.
Пользователь не получает ни ошибки, ни подтверждения, видит «ничего не произошло».

### Steps to Reproduce
1. Зарегистрировать Host, добавить навык и свободный слот на завтра, 12:00
2. В **отдельном контексте** зарегистрировать Guest
3. Guest открывает страницу участника Host
4. **Сразу после загрузки страницы**, до полной гидрации React (визуально — между DOMContentLoaded
   и моментом, когда кнопки реагируют на hover/focus), кликнуть «Забронировать»
5. Открыть DevTools → Network: фильтр по запросам бронирования — нет outgoing запроса
6. Открыть «Мои встречи» у Guest — встречи нет

### Expected Result
Один из вариантов (выбор за продуктом):
1. Кнопка `disabled` до завершения гидрации — пользователь не может кликнуть
2. Клик регистрируется, на нём висит показыватель загрузки (spinner/disabled), запрос уходит после гидрации
3. После клика пользователь видит явное сообщение «Подождите, идёт загрузка» или ошибку

### Actual Result
Клик — тихий no-op. Запрос не отправляется. UI не меняется. Гость уверен, что кнопка
«не сработала», и может кликнуть ещё раз — это приводит к флаки-тестам и реальной
потере сценариев у пользователей с медленным устройством / сетью.

### Evidence
- Trace.zip с воспроизведением: момент клика и пустой Network
- Воспроизводимость: ~30% на CI без ретраев, ~5% локально (зависит от того, когда Playwright успевает кликнуть)
- Лог из Allure: «No outgoing request for /bookings after click on [data-testid='book-button']»

### Impact
- **Кто затрагивается:** все пользователи после перезагрузки страницы; сильнее — пользователи
  с медленным устройством / сетью / первый визит (когда чанки долго подгружаются)
- **Частота:** воспроизводимо, но не always — зависит от тайминга гидрации
- **Workaround:** обновить страницу и кликнуть заново (пользователь не знает, что нужно делать именно это)
- **Затронутые тесты:** все `e2e/*` тесты, где есть клик после `goto()`. До митигации — flaky;
  после митигации (ретраи в page objects) — стабильно

### Root Cause
Кнопка рендерится на стороне сервера сразу (SSR/статический HTML), обработчик навешивается
только после гидрации React-компонента. Между этими моментами кнопка видима и в DOM,
но обработчик `onClick` ещё не подключён. Playwright умеет «auto-wait» по DOM, но не по
React-дереву готовых обработчиков — для него кнопка готова с момента, когда она visible
и stable.

### Suggested Fix
1. На время до гидрации ставить на кнопки `disabled` или `aria-busy="true"`
2. После гидрации снимать флаг — тогда Playwright `expect(button).toBeEnabled()` начнёт
   auto-wait корректно
3. Альтернатива — `data-hydrated="true"` атрибут на `<body>`, page objects ждут его

### Митигация в тестах
В page objects клики обёрнуты в retry до получения ответа сервера
(`expect.poll(() => pageHasResponded())` или эквивалент через `Promise.race`).
Это лечит flaky, но не лечит UX для реальных пользователей.
