# Матрица покрытия PomidorQA

Покрытие считается по функциональным требованиям MVP из спецификации курса (50 требований,
R3–R12), а не по числу файлов и не по строкам кода продукта. Playwright тестирует PomidorQA
как чёрный ящик: исходники приложения в этот репозиторий не входят, поэтому code coverage
здесь измерить нечем.

Каждое требование получает один из четырёх статусов.

| Статус | Что означает |
|---|---|
| `automated` | есть автотест, который падает, если поведение сломается |
| `partial` | покрыта наблюдаемая часть правила, серверная или скрытая — нет (примечание у строки) |
| `known defect` | требование не выполняется продуктом; тест по требованию помечен `test.fail()` |
| `out of scope` | состояние недостижимо через интерфейсы продукта, black-box проверить нечем |

Срез: **23.09.2026**, ветка `main`, стенд `https://aiqa.su/pomidorqa`.

## Известные дефекты

### KD-1 — каталог ищет по навыкам обоих типов

Требование R8.3 ограничивает поиск разделом «могу помочь», фильтр каталога проходит по всем
навыкам участника: по запросу навыка из «хочу разобрать» тоже находятся люди. Это дефект
продукта: требует решения — сузить фильтр или переписать требование.

План: тест по требованию с `test.fail()` (файл `e2e/known-defects`). Пока дефект жив,
тест падает и висит в отчёте как сигнал; прогон остаётся зелёным. Когда продукт починят,
Playwright скажет «expected to fail, but passed» — это сигнал снять пометку.

Урок эталонной матрицы, применимый дословно: зелёный тест, фиксирующий дефект как норму,
опаснее отсутствующего теста.

## Закрытые проблемы набора

Проблемы, найденные собственными прогонами и зафиксированные в инфраструктуре набора.

### Гонка клика с гидрацией React → ретраи до ответа сервера

Стенд — SSR Next.js: клик по кнопке до завершения гидрации — тихий no-op (обработчик ещё
не прикреплён), запрос не уходит, а `waitForResponse` зависает. Найдено в guest-access,
подтверждено трейсом: после `page.reload()` за 90 секунд не ушло ни одного запроса.

Лечение: `save()`, `removeSkill()`, `deleteFirstFreeSlot()` ретраят клик до ответа сервера
(`toPass` + `waitForResponse` с коротким таймаутом), `waitForFreeSlot()` перед релоадом
ждёт URL страницы участника.

### Осиротевшие аккаунты на общем стенде

Падение до `afterEach` оставляет аккаунт на стенде навсегда. Осиротевший хост с именем,
совпадающим по подстроке с именем следующего прогона, ломал поиск карточек
(«catalog-host Автотест» матчится фильтром «host Автотест»). Правило набора: только
`makeUser`/`makeUnique`, никаких статичных тегов — тогда сирота инертна.

### Зелёный ассерт не того блока

Проверка навыка «хочу разобрать» сначала писалась через локатор блока «Могу помочь» —
ассерт был всегда зелёным и ничего не проверял. Урок: ассерт валиден, только если локатор
указывает на тот элемент, в котором ожидается эффект.

## Уровни проверок

| Уровень | Тестов | Что проверяет |
|---|---|---|
| unit | 10 | чистые функции набора: пересечение слотов, валидация пароля, формат времени |
| api | 8 | бизнес-правила брони на мок-сервере (`src/pyramid/`) |
| e2e | 28 | пользовательские сценарии на `aiqa.su/pomidorqa` |

Честная оговорка про пирамиду: unit-уровень проверяет **наш собственный** код, а не
продукт — исходников PomidorQA у набора нет. Широкое основание пирамиды в этом проекте
недостижимо в принципе, и это нормально для внешней автоматизации чёрного ящика. Правила
брони, которые дешевле проверять ниже UI, вынесены на API-уровень.
